# 較正ループツール

## これは何か・なぜ要るか

Novel Quality Filter は、小説の本文を統計的に分析して 0〜100 の「品質スコア」を付ける。
このスコアが、開発者本人の直感とズレることがある ── 具体的には、**面白い作品が中途半端な
点数で止まってしまう**。原因のひとつは、「一文一段落率」（段落がほぼ全部一文で構成される
割合。会話主体の作品ほど高くなる）という指標のペナルティを効かせすぎていること。

この仕様は、その**スコアのズレを直すための開発用ツール**を定める。本番の Chrome 拡張の
採点そのものを変えるものではなく、採点式（各指標の重み・ペナルティ）を**安全に試行錯誤する
ための作業台**である。

ツールの本体は一言で言える ── **採点式を変えたとき「悪い作品は悪いまま据え置きで、いい作品
だけスコアが上がる」状態を確認できること**。作品メタ情報（タイトル・作者・レビュー数）や
各指標の内訳を一覧で見られるのは、その確認を助ける付随機能である。

### 真値は開発者の直感（オラクル）

「いい作品／悪い作品」の正解は、レビュー数や星の数のような客観指標ではなく、**開発者本人が
本文を読んで下す判定**とする。これを較正の「オラクル（真値）」と呼ぶ。ツールはこのオラクルに
定量スコアが追従できているかを見るための道具であり、機械や LLM が良し悪しを判定して真値を
置き換えることはしない（後述）。

## 較正ループ

このツールは次のループを回すために作る。

1. **登録** ── 比較対象になる作品を 20〜30 本、手で選んで集める（良作・駄作・その中間や
   紛らわしいものを混ぜる）。
2. **ラベル付け** ── 集めた各作品に、開発者が本文を読んで「良／悪」の判定を付ける。
3. **現状の評価を確認** ── 今の採点式でのスコアを見る。
4. **式を弄る** ── 実験用の採点式を書き換える（重みを変える、新しい指標を足す等）。
5. **適用して一覧で比較** ── 実験式でスコアを付け直し、「良ラベルの作品だけ上がって、悪ラベル
   は据え置きか」を一覧で見る。
6. 2〜5 を繰り返す。

作品数を 20〜30 本の**厳選**に絞るのは、全作品に手でラベルを付けるのは破綻するからで、
少数のよく選んだ標本（アンカー）で式の妥当性を検証する、という前セッションからの方針を継ぐ。

## ツールの4機能

ツールが提供する機能は次の4つに限る。

### 登録

指定した作品（URL または作品ID）を集めて、ローカルに保存する。これは既存の収集の仕組みを
そのまま使う ── 本文の生 HTML を「原本」として凍結保存し（後で再取得せずに何度でも
再計算できる）、分析結果をデータセットに追記する。カクヨムへの過剰アクセスを避けるレート
制限（取得間隔・話数上限）もそのまま守る。**新しい収集経路は作らない。**

作品のタイトル・作者・レビュー数などのメタ情報は「取得時点の控え」として保存し、再取得の
たびに上書き更新してよい。これらは参考情報なので、本文のように「不動の原本」として厳密に
保存し直す仕組み（作品紹介ページの HTML 保存など）は作らない。

### 評価

集めた作品を採点式に通してスコアと指標内訳を計算する。**このスコアは保存済みの値をそのまま
表示するのではなく、その時点の式（正本または実験式）で毎回計算し直す。** 較正中は式が動く
ので、収集時に保存した古いスコアを「現在のスコア」として扱うと値が化石化して比較が壊れる
（既存の分析スクリプトはこの取り違えの不具合を抱えている）。

### 詳細（廃止：viewer に統合）

かつては `cal detail` サブコマンドが1作品ぶんの分析票を単独の HTML として出していたが、
これは廃止した。詳細分析票（作品メタ情報、各指標の値と正規化後スコア、判定フラグ、
ペナルティ、行単位のメタデータ）は、下記「一覧」が焼く `cal.json` からブラウザ側の
ビューアが描画する（詳しくは「viewer の実装方式」節）。分析票のレイアウトが本番拡張の
詳細カードと同じものを目指す方針は変わらない。

### 一覧

ラベル付き作品を並べ、各作品について **良／悪ラベル・正本式のスコア・実験式のスコア（および
その差分）**を横に並べて確認できるようにする。較正ループの中心画面であり、「良ラベルだけ
スコアが上がって悪ラベルは据え置きか」をここで一目で確認する。

出力は単一の `cal.json`（全作品ぶんの識別情報・meta・rawMetrics・正規化後スコア・ ScoreResult
内訳・LineMetadata・ラベルを横並びで持つ）で、描画はブラウザ側のビューア （`cal serve`
が配信する静的 HTML/JS）が担う。1作品の詳細分析票も同じ `cal.json` から ブラウザ側で開く（旧
`cal detail` サブコマンドは廃止）。詳しい構造は「viewer の実装方式」 節を参照。

## 採点式の実験方式

採点式の正本は `src/domain/scoring/weights.ts`（各指標の重み・正規化・ペナルティの定義）に
ある。**この正本は較正ツールから一切書き換えない。**

代わりに、正本と同じ型（interface）だけを共有した実験用の式定義（例 `weights_experiment.ts`）を
別に用意し、そこに試したい式 ── 重みの変更や、新しい評価軸（例：地の文の短文率）の追加を 含む ──
を書いて、ツールにはそちらを食わせる。こうすることで、正本を汚さずに好きなだけ式を
試せる。新しい変種を足すときも、既存の式やコードには手を触れない（拡張は追加で行う）。

## 既存基盤の再利用と、使い捨ての削除

較正のための収集・保存の土台 ── 原本の凍結保存、原本からの再計算（凍結した採点手順に従って
再現する経路と、現在のロジックで選び直す実験用の経路を分けてある）、データセット、ラベル ストア ──
は既に完成しており、そのまま再利用する。これらの「再現の約束」（凍結した手順で
採点する・再取得しない・原本を書き換えない）は壊さない。

一方、`scripts/` 直下に溜まった単発の実験用スクリプト（1本の URL を採点して表示するもの、
ローカルテキストを採点するもの、固定テスト素材を出すデバッグ用、無作為クロール、複数の実験
ハーネス、分離度計算など）は、上記4機能ができれば役目を失うので**ほぼ全て削除する**。削除
するのは「使い捨ての入口」であって、その下で使われている基盤ロジックは残す。

無作為にタグを巡回して母集団を広く集めるクロール機能は、今回の「手で 20〜30 本を厳選する」
運用では不要なので廃止する。

## LLM の役割

このツールで「LLM に分析させる」とは、**LLM に作品の良し悪しを判定させることではない**。
真値は開発者の直感（オラクル）であり、LLM に良／悪を先に判定させると真値が LLM の出力に
引きずられて汚染される。また「本文を先に読んでから数値を見る」という盲検の順序（数字を先に
見ると『やっぱり駄文』の後付けで判定が歪む）も崩れる。

LLM の役割は、作品数が多くて人手では見きれないときに、**一覧化された分析結果を眺めて
「いい作品が不当に沈んでいる原因の仮説」や「次に人が確認すべき作品」を拾い出す補助**に
限る。判定者ではなく、開発者が判断を下すための材料整形役である。

## 受け入れ条件

- 実験式を差し替えて評価を実行でき、その操作で正本 `weights.ts` は変更されない。
- 一覧が、各作品について 良／悪ラベル・正本スコア・実験式スコア（差分）を並べて表示する。
- 一覧・詳細のスコアは、保存済みの値ではなく現在の式で計算し直した値である。
- 詳細ビュー（ブラウザ側ビューアの詳細パネル）が、1作品のメタ情報・指標内訳（正規化・
  フラグ・ペナルティ）・行メタデータを表示する。
- 登録は既存の収集経路（原本凍結・データセット追記・レート制限）を用い、新しい収集経路を作らない。
- 削除後、`scripts/` 直下に使い捨ての実験入口が残らない（登録／評価／一覧／配信の機能入口のみ。
  詳細はブラウザ側ビューアに統合され、独立したサブコマンドではない）。
- 新ツールが既存基盤の再現の約束（凍結手順での採点・再取得しない・原本不動）を壊さず再利用する。
- 「良作だけ上がり駄作は据え置き」を、良／悪ラベル別のスコア変化として一覧で確認できる。

## viewer の実装方式（データと描画の分離）

較正ループの「一覧」と「詳細」の描画は、**採点結果を JSON で焼き、静的な HTML と JavaScript で
描画する**構造をとる。以前は Deno 側で HTML 文字列を組み立てていたが、その方式は本文由来の 文字列を
HTML に埋める経路（XSS 経路）を毎回意識しないと安全に保てず、また LLM に読ませて
傾向を掴ませたいときに HTML のレイアウトがノイズとして混じる。データと描画を分ければ、
両方の問題が構造的に消える。

### 出力は cal.json 1本

`cal list` の出力は **単一の `cal.json`** とする。全作品ぶんの識別子・meta・rawMetrics・
正規化後スコア・ScoreResult 内訳（正本式・実験式）・LineMetadata・ラベルを、作品ごとの
オブジェクトに横並びで持たせる。ここに全部載せることで、指標同士の横並び比較
（例：平均文字数と地の文の短行率）を追加のファイル読み込みなしで行える ── これが較正ループの
中核の使い方だからだ。

作品ごとの詳細分析票のためだけに別ファイルを吐く形（`cal-work-{id}.json` などの分割）は
採用しない。実用レンジ（想定 100〜200 本）の総サイズは数百 KB〜1 MB に収まり、ブラウザで 1回の fetch
で描画でき、LLM に丸ごと食わせるにも余裕がある。将来サンプルが数千本に伸びて
重くなったら、そのタイミングで分割へ移す。

`cal detail` サブコマンドはこのため廃止する。1作品の詳細もブラウザ側で `cal.json` の中から
該当作品を選んで描画する。

### 描画はブラウザで、Preact + htm を CDN 経由で

静的な `index.html` から Preact と htm を CDN で読み込み、`cal.json` を fetch して一覧テーブル
＋詳細パネルを描画する。ビルドは必要としない ── これは開発ツールなので、試行錯誤のしやすさ
（ビルド待ちなしで assets を弄れる）を優先する。CDN 依存はオフラインでは動かなくなるが、
開発時の実害としては受容できる。

数値の表示整形（率のパーセント表示、平均字/行のフォーマットなど）は、Deno 側の
`src/domain/analyzer/dossier_format.ts` にある純粋関数の JavaScript 版を、ブラウザ側で別途
実装する。同じ入力に対して同じ出力を返すことをテストで担保する。関数は 10 行前後で数個しかない
ので、共通モジュール化のコストを払うより再実装で十分と判断する。

### 配信は cal serve サブコマンド

ブラウザから `cal.json` を fetch するには HTTP 越しに開く必要がある（`file://` で開くと CORS で
拒否される）。このため `cal serve` サブコマンドを追加し、Deno.serve で dist ディレクトリを配信
する。デフォルトでは起動時にブラウザを自動で開き、`--no-open` で抑制できる。

`cal list` と `cal serve` は独立コマンドとする。ホットリロード（assets や `cal.json` の
変更を検出して自動リロード）は初版では入れない。較正ループの主なワークフロー （実験式を弄る →
`cal list` を再実行 → ブラウザを手動リロード）は手動リロードで十分に回るからだ。

### 配置と設定は環境依存

`cal.json` の出力先（dist ディレクトリ）と `cal serve` のポート番号は環境依存の値として扱い、 config
ファイルで上書き可能にする。config の実体は `.agents/runtime/cal-viewer/config.json` （.gitignore
済みディレクトリ内）に置き、テンプレとして `scripts/lib/cal_viewer/config.example.json`
を配布する。config なしでもデフォルト値（dist_dir=`.agents/runtime/cal-viewer/dist`,
port=8000）で動くように設計する。

ビューアのソース資産（`index.html` / `app.js` / `style.css`）は `scripts/lib/cal_viewer/` に
置き、`cal serve` は起動時にこれらを dist ディレクトリへコピーしてから配信する。ソースは
リポジトリで管理するが、生成物（dist と cal.json）はリポジトリに載せない。特に **cal.json は
作品本文由来のメタ情報を含むため、著作権上の理由で git 管理下に置かない** ── デフォルト出力先が
`.agents/runtime/` 以下（.gitignore 済み）にあるのはこの制約を満たすための選択である。

## 受け入れ条件（viewer の実装方式について追加）

- `cal list` は単一 `cal.json` を出力し、全作品分の rawMetrics・正規化スコア・ScoreResult
  内訳（正本と実験式）・LineMetadata・meta・ラベルを含む。
- `cal detail` サブコマンドは存在しない。1作品の詳細は `cal.json` からブラウザ側で描画する。
- `cal serve` サブコマンドが config を読み、dist ディレクトリを HTTP で配信する。デフォルトで
  ブラウザを自動で開き、`--no-open` で抑制できる。
- config ファイルなしでもデフォルト値で `cal list` と `cal serve` が動く。config がある場合は
  その値で上書きされる。
- ブラウザ側のビューアは Preact と htm を CDN から読む以外の外部依存を持たない。
- ブラウザ側の数値整形（`format.js`）が Deno 側の `dossier_format.ts` の対応関数と同じ入力に
  対して同じ出力を返すことを、Deno テストで検証する。
- 生成物（dist と cal.json）は git 管理下に載らない。

## viewer の UI 構成（サイドバー・並列比較・行データ可視化）

較正ビューアの UI レイアウトを、実運用の操作性と較正判断の材料密度を両立するかたちで定める。
実サンプルが青天井（100〜200 本〜）で伸びること、実験式のデルタが指標単位で細かく効くことを
前提に組む。

### レイアウト: サイドバー + Detail の 2 pane

ページ全体は左サイドバー（作品一覧）と右メイン（Detail）の 2 pane grid で構成する。
サイドバーは開閉トグルで切り替わり、開状態は幅 320px、閉状態は幅 48px のアイコンバーになる。
開閉状態は localStorage に保存し、次回起動時に復元する ── 一度閉じたら開き直さず detail に
集中できる。

作品数が伸びても操作性を落とさないため、サイドバーは viewport 内で sticky にして、リスト
だけが独立にスクロールする。

### サイドバーの絞り込みと並び

サイドバー上部に、較正ループの実運用で必要な絞り込みを配置する。

- **検索**: タイトルまたは作者の部分一致で絞る
- **ラベルフィルタ**: 良／駄／対象外／未 の 4 チップ。複数選択（OR）で作動し、選択状態は
  ラベルのセマンティック色（良＝forest、駄＝terracotta、それ以外＝accent）で表示する
- **用途特化フィルタ**: 較正で頻用する複合条件のプリセット
  - **要注意**: canonical または experiment のいずれかで 1 つ以上の指標が flagged になって
    いる作品。良ラベルなのに flag が立っていれば「ペナルティ設計を疑う材料」、駄ラベル なのに flag
    が無ければ「検知漏れの材料」になる
  - **実験影響大**: `|experiment.score − canonical.score| ≥ 3` の作品。実験デルタを
    弄ったときに「大きく動いた作品」を先に確認する使い方を想定
- **ソート dropdown**: Δ（実験 − 正本）降順 / 正本降順 / 実験降順 / ラベル / タイトル。 デフォルトは
  Δ 降順（較正で最も見たい観点を先に見せる）

これらの絞り込みは AND で合成する（例: ラベル「良」× 要注意 = 良ラベルなのに flag が立って
いる作品）。

### Detail: 指標内訳は正本 × 実験の並列表

Detail の指標内訳セクションは、canonical と experiment を別セクションで並べるのではなく **1
テーブルに並列**で並べる。1 行が 1 指標に対応し、raw / 正 normalized / 正 weight / 正 contribution /
実 normalized / 実 weight / 実 contribution / Δ contribution の 9 列で
構成する。差分がある行は淡いインディゴで背景着色して、差分の所在を一目で識別できるように する ──
差分ゼロ状態では 0 行が着色されるだけで UI は破綻しない。

ペナルティも同じ原則で並列表示する。正本と実験の乗算率を横に並べ（正 ×0.X / 実 ×0.X）、
片方だけ発火する状態も可視化する。

### Detail: rawMetrics は単一表示のまま

rawMetrics（16 項目）は本文由来で正本／実験式のどちらでも同じ値を返すため、単一表示で扱う。 採点対象
12 項目と非採点 raw のみ 4 項目（`charCount` / `sentenceCount` / `separatorCount` /
`dialogueCount`）を区別せず、全 16 項目を並列に見せる方針は前 iterate 通りで継続する。

### Detail: 行データを Chrome 拡張と同等の粒度で可視化する

行データ（LineMetadata）は「新しい指標を weights_experiment に足すかどうか」を判断する
一次材料になる。生 JSON の展開では判断できないので、Chrome 拡張の詳細カード（作品ページに
差し込む「行メタデータ」セクション）と同等の粒度で可視化する。

具体的には、行データセクションは以下で構成する。

- **総サマリ**: 総行数・総文字数・空行数（率）・区切り線数（率）を並べる。上に「平均字/行」
  「地の文短行 30%」のような較正判断の焦点になる指標をチップで強調する（閾値超えは色で明示）
- **色帯**: 6 区分（地の文／セリフ／メタ／非文末／空行／区切り）を行数比率で塗り分けた 1
  本の帯。凡例で各区分の色と比率を示す
- **カテゴリ別カード**: 地の文／セリフ／メタ／非文末の 4 カード。各カードに「行（数・比率）」
  「文字（数・比率）」「短行 20/30（率）」を並べ、地の文カードには「短チャンク 20/30」も
  含める。短行率が閾値を超えるとカード内で色で警告する

行データの集計・数値整形（総サマリ・色帯の区分幅・カテゴリ別内訳・短行/短チャンク比率の warn
判定など）は新設 `scripts/lib/cal_viewer/line_meta.js` に実装する（`format.js` は
既存の低レベル整形関数の置き場のまま変更しない）。line_meta.js は Deno 側
`src/domain/analyzer/dossier_format.ts` の対応関数（`averagePerLineLabel` / `averageCharsLabel` /
`compositionSegments` / `percentInt` / `percentOne` /

### 見え味の基準（パレット・タイポグラフィ）

配色は warm off-white を ground（`#FBF8F2` / dark: `#16181C`）に、深いインディゴを唯一の
accent（`#3A4F87` / dark: `#7C8FCD`）にする。データセマンティックとして良（forest
`#3F7C55`）／駄（terracotta `#B0533A`）／flag（amber `#C88A2B`）の 3 色を、それぞれの
用途にだけ使う。dark theme もパレットセットで揃える。

書体は日本語含めて system sans に統一し、数値表示は `font-variant-numeric: tabular-nums`
を徹底する。見出しに serif は使わない ── データダッシュボードとして落ち着いた可読性を優先
する。詳細レイアウトの参照実装は wrap 時のモック（Artifact URL は idea memo に記載）とする。

## 受け入れ条件（viewer の UI 構成について追加）

- ページが sidebar（左）+ main（右）の 2 pane grid で描画され、サイドバーは開状態 320px / 閉状態
  48px で切り替わる。開閉状態は localStorage に保存され次回起動時に復元される。
- サイドバーが検索・ラベルフィルタ（4 チップ、複数選択 OR）・用途特化フィルタ（要注意 /
  実験影響大）・ソート dropdown（5 種、デフォルト Δ 降順）を持ち、複数条件は AND で合成される。
- 「要注意」は canonical か experiment のいずれかで 1 つ以上の指標が flagged になっている
  作品に絞る。「実験影響大」は `|experiment.score − canonical.score| ≥ 3` の作品に絞る。
- Detail の指標内訳が 1 テーブルに 12 行、raw / 正 norm / 正 wt / 正 寄与 / 実 norm / 実 wt / 実
  寄与 / Δ 寄与 の 9 列で表示され、差分がある行は淡いインディゴ背景で強調される。
- Detail のペナルティが正本 × 実験の乗算率を並列表示する。
- Detail の行データセクションが総サマリ + 色帯 + カテゴリ別カードで構成され、Chrome 拡張の
  詳細カードと同等の粒度を持つ。行データ整形関数は Deno 側 dossier_format.ts と同期テストで
  一致が担保される。
- rawMetrics は現状（単一表示・全 16 項目）を維持し、正本/実験の並列化はしない。
- スコア差分ゼロ状態でも UI が破綻せず、差分カラムが 0、実験カードが正本と同じ数字を表示し、
  差分行の背景着色は発生しない。

## viewer の Web ラベル編集

較正ビューアの DetailPanel から、ブラウザだけでラベル（良／駄／対象外／未ラベルに戻す）を
編集できるようにする。CLI (`cal label`) は残すが、実運用では Web 編集が主動線になる。 CLI
の摩擦は「作品を Web で確認 → ID をコピー → ターミナルへ貼り付け → コマンドを打つ」
という往復コストであり、Web 化はその一手を消すことに絞る。

### UI パターン: chip をクリック → その場に popover 展開

Detail の meta-header にあるラベル chip をクリック可能ボタン化する。押下すると chip の 直下に小さな
popover が浮き、中身は 良／駄／対象外／未ラベルに戻す の 4 択を縦に並べる。 選択 = 即 API 呼び出し +
optimistic UI + auto-close で、編集は 2 手（chip をクリック → 値を選ぶ）で完結する。

「常時 Edit 表示」（Detail に操作パネルを固定表示する案）は、読み時の視覚ノイズが常に
居座って落ち着かないため採らない。モーダル + 確定ボタン方式（オーバーレイ表示 → 選択 → 確定クリック
→ ローディング → API → 閉じる）も検討したが、3 値単純上書きに対して重すぎるため 今回は採らない。将来
tags / note の複合編集を統合するときにモーダルへ格上げする道は残す。

### Detail の chip はサイドバーよりひと回り大きく

Detail の chip はクリック可能な操作対象なので、サイドバー行の chip（font 10px / padding 1px 6px /
border-radius 3px）よりひと回り大きい font 13px / padding 4px 10px / border-radius 4px
にし、右端に小さな `▾` caret を添えてクリック可能を示唆する。サイドバー の chip
は既存サイズを維持する（一覧の情報密度を優先）。

### 未ラベルに戻す = labels.jsonl から行削除

ラベルは「その作品を分析に使うかどうかのマーカー」であり、サンプルとして不適だと後から
判断したら外せる必要がある。「未ラベルに戻す」は `labels.jsonl` から該当行を削除する
アクションで、chip 表示は unlabeled 状態（点線 dashed）に戻る。

### サーバー側: cal serve を read-only から read-write へ拡張

`cal serve` に POST エンドポイントを追加し、`labels_store.setLabel` を再利用してラベル
更新を受ける。「未ラベルに戻す」用の行削除ヘルパを `labels_store` に新設する。localhost 限定バインド
(127.0.0.1) は維持する。

`cal serve` はラベル変更時、対応する `cal.json` エントリの `labels` フィールドだけを差分 patch
する（fast-path）。作品の metric 再計算・score 再計算・エントリ追加を含む全 build は 依然 `cal list`
の責務で、`cal serve` からは scoring 依存を持たない。両者の責務境界を混ぜず、 Web 編集は「labels
フィールドの上書き」だけに閉じる。

書き込み系ハンドラは Deno のシングルスレッド実行下で Promise chain により直列化する
（read-modify-write の race で labels.jsonl の更新が消えるのを防ぐ）。labels.jsonl と cal.json
の書き込みは tmpfile + rename の atomic write に統一し、書き込み途中のクラッシュで
半端に壊れた状態が残らないようにする。

同一プロセス内で CLI と Web が併走する運用は許容する（labels.jsonl は追記ではなく既存 レコードの
upsert / delete で書き換えるため、CLI と Web の同時操作は last-write-wins に
なる。個人用途で並走頻度は低い前提）。

### 失敗時の挙動

POST が失敗した場合は toast で通知し、chip 表示を操作前の状態にロールバックする。 optimistic UI
で先に UI を更新している以上、失敗が静かにズレを残すのが一番怖いシナリオ
なので、失敗ハンドリングを省略しない。

### 操作の詳細（popover の閉じ方など）

popover は外側クリック / ESC キー / 値選択 のいずれでも閉じる。focus は popover 内へ
移動し、閉じたら元の chip に戻す（キーボードアクセス性）。同時に複数の popover を開かない （1 作品 1
popover）。

### 参照実装

具体的な見た目・レイアウト・色使いは wrap 時のモック v8.2 を参照する（Artifact URL は idea memo
に記載）。

### 「対象外」ラベルの扱いと primary chip 選定規則

ラベルは 2 軸で持つ (品質: 良/駄、スコープ: 対象/対象外)。「対象外」を選んだ時、
過去に付けた品質判定 (良/駄) は破棄せず保持する。理由は、対象外にする動機が多様
（連載停止、非小説、様子見、後で再判定したい）で、破棄すると「一時的に対象外」の
使い方が壊れるためである。連載停止した作品もサンプルとしては価値があり、判定した
品質を残す方が自然。

品質を明示的に消したい場合は、popover の「未ラベルに戻す」を使う。これは labels.jsonl
から該当行を丸ごと削除するアクションで、品質・スコープの両方を 同時に消す。品質だけ /
スコープだけを部分的に消す UI は提供しない (単一の 削除経路に集約)。

Detail の meta-header に表示する chip (primary chip) の選定は、スコープ軸を 優先する。scope="対象外"
なら chip 表示は「対象外」、scope="対象" かつ quality が設定されていれば chip
表示は「良」または「駄」、両方 undefined なら chip は「未」(点線 dashed)
を出す。この順序により、「対象外にしたのに chip が
以前の判定を出し続ける」という表示のズレが起きない。

サイドバー行の chip も同じ選定規則を適用する。

## 受け入れ条件（Web ラベル編集について追加）

- Detail の meta-header に表示されているラベル chip がクリック可能ボタンで、押下すると popover
  が展開される。
- popover 内の 良／駄／対象外 を選択すると即座に POST が飛び、labels.jsonl が更新され、 popover
  が閉じて chip の色と文言が新値に切り替わる。
- popover 内の「未ラベルに戻す」を選択すると labels.jsonl から該当行が削除され、chip が unlabeled
  表示（点線 dashed）に戻る。
- POST が失敗した場合は toast で通知され、chip 表示が操作前の状態にロールバックされる。
- popover の外側クリック / ESC キーで popover が閉じ、focus が元の chip に戻る。
- Detail chip のサイズが font 13px / padding 4px 10px / border-radius 4px、サイドバー chip は既存の
  font 10px / padding 1px 6px / border-radius 3px のまま。
- `cal serve` が POST を受け付け、localhost 限定バインド (127.0.0.1) が維持される。
- `cal label` CLI が引き続き動作し、`駄` 値を受理する。
- 「対象外」を選択しても既存の quality (良/駄) は保持され、labels.jsonl の 該当行に quality
  フィールドが残る。対象外を解除して「良」または「駄」を選ぶと、
  以前の判定は上書きされる形で更新される。
- Detail およびサイドバーの primary chip は scope 優先で表示される。 scope="対象外"
  なら「対象外」、対象なら quality、両方 undefined なら「未」。

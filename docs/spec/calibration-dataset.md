# 較正データセット（行メタ指標の評価軸昇格に向けた収集・保存）

このドキュメントは、小説の文体品質スコアを較正（キャリブレーション）するための
「サンプルの集め方・貯め方・ラベルの付け方」を定める仕様である。ここでいう較正とは、
スコアの計算式が実際の良し悪しと合うように調整する作業を指す。

## 背景と目的

既存スコアは12個の指標（文長のばらつき、段落の均質さなど）で本文を採点している。
しかし「1行あたりの情報量が少ない」駄文——会話文が主体で、ステータス画面のような
装飾行が並び、短い行ばかりの作品——は、この12指標をすり抜けて閾値（現在40）を 超えてしまう。

そこで前段で本文を行単位に分類し、次の3つの指標（本ドキュメントでは「行メタ指標」と
呼ぶ）を診断表示できるようにした。

- **平均字/行**：空行を除いた1行あたりの平均文字数。少ないほど中身が薄い疑い。
- **地の文短行率(30)**：セリフでも装飾でもない「地の文」のうち、30文字未満の
  短い行が占める割合。高いほど内容の薄い地の文が多い疑い。
- **メタ率**：ステータス画面・章題・装飾記号など「本文でない飾りの行（メタ行）」が
  全行に占める割合。高いほど飾りで水増ししている疑い。

**本仕様の目的**は、この3指標を単なる表示から一歩進めて、既存12指標を考慮しても
なお良作と駄文を追加で分けられるか（＝評価軸へ昇格できるか）を実測するための、
ラベル付きサンプルを収集・保存する仕組みを定めることである。

## 基本方針

### 真値はユーザーの直感

品質の「正解」は、レビュー数や星の数のような客観的な代理値ではなく、
**ユーザー自身の直感的な判定**とする。ユーザーが駄文と感じたものは実際に品質が低い、
という前提に立つ。最終目標は「定量スコアの出力がユーザーの判定と食い違わないこと」で ある。

### ラベルは全件に付けない（厳選アンカー方式）

全作品に手で良し悪しを付ける運用は、量が増えると破綻する。そこで主観判定は
**厳選した少数（数十本規模）の基準サンプル**にのみ付ける。この基準サンプルを
本ドキュメントでは「アンカー」と呼ぶ。アンカーの役割は学習用の大量データではなく、
**計算式が誤判定した瞬間を捕まえる反証セット**である。主観のコストは作品数に
比例せず、数十本で頭打ちにする。

### 盲検の順序

ラベルを付けるときは、**先に本文だけを読んで良し悪しを判定し、その後で数値を確認する**。
スコアや行メタの数字を見てから判定すると「やはり駄文だと思っていた」という後付けが
起き、判定が数値に引きずられる。すると「行メタ指標が判定と相関する」という結論が
循環論法になる。順序を守ることで、真値としての判定を汚染から守る。

### ハードネガティブを必ず含める

すり抜け駄文（会話主体・短行・装飾多め）だけを集めて式を組むと、出来上がるのは
「Web小説的なレイアウトを一律に罰するだけの機械」になりかねない。テンポ重視で
短い地の文を意図的に多用する**上手い作品**まで巻き込んでしまう。これを防ぐため、
「**駄文と同じ見た目なのに良作**」な作品（ハードネガティブと呼ぶ）を対照群として
意図的にアンカーへ含める。式がこれらを正しく通過させることを確認するためである。

## 保存設計

### 原本は生HTML、派生は使い捨て

較正の土台は、カクヨム等から取得した**生のHTMLそのもの**とする。一度取得したら
二度と取り直さなくて済むように、採点に使ったHTMLを捨てずにローカル保存する。

- **不動の原本**：取得した生HTMLと、その採点手順を記録した小さなメモ（後述の manifest）。
  ここは一度書いたら作り替えない。
- **使い捨ての派生**：12指標や行メタの計算結果（数値）。これらは原本から
  いつでも再計算できるので、キャッシュ（一時的な控え）として扱う。新しい指標を
  思いついたら、保存済みHTMLを読み直して数値を作り直すだけでよく、
  取得のやり直し（再フェッチ）は不要。

### 再導出保証の範囲（正直な線引き）

「二度と作り替えない」は原理的に無制限には保証できない。保証する範囲は
**本文・行に基づく指標まで**とする。将来、公開日・エピソード一覧・動的に生成される
画面要素など、いま保存していない情報を必要とする指標が出てきた場合は、
その指標については再フェッチが必要になる。この境界を明示しておく。

### 保存するのは採点対象の話だけ（全話ではない）

保存対象は、採点処理が実際に取得した**冒頭の数話（通常1〜2話）だけ**である。
作品に存在する全話をダウンロードするわけではない。採点処理は先頭話から順に、
サンプリング判定が「これで十分」と決まるまで連続して話を取得する。その過程で
取得した話はすべて保存する（採点対象に選ばれた話も、そうでない話も含む）。
これにより、開幕形式の判定やサンプリングのやり直しを、取得済みHTMLだけで オフライン再実験できる。

補足：スコアは複数話をつなげて評価する場合がある（本ドキュメントでは「+n連結」と
呼ぶ。先頭からn話ぶんの本文を連結して1つの採点対象とする方式）。この連結を
再現するため、取得した話は順序付きで保存する。

### 取得物の健全性検証

保存する前に、そのHTMLが**本物の本文ページであること**を検証する。具体的には
HTTP応答が正常（200）で、本文の抽出に成功していることを確認する。エラーページ・
年齢確認ページ・bot対策ページなどを「不動の原本」として保存してしまうと、
後から取り直せない場合に修復不能となり、データセット全体の信頼性が崩れるためである。

## データ配置

作品1件ごとに、取得した話のHTMLと1つの manifest（採点手順のメモ）をまとめて置く。

```
.agents/runtime/
├── dataset.jsonl        # 1行=1作品。計算済みの数値（12指標＋行メタ）＋原本への参照
├── labels.jsonl         # 1行=1作品。ユーザーの判定（品質／スコープ）
└── pages/
    └── kakuyomu_822139843750356709/       # サイト名_作品ID ごと
        └── 2026-08-10T07-47-15-123Z/       # captureId（取得スナップショット）ごと
            ├── 000_<話ID>.html             # 取得した話（採点対象・非対象を問わず全部）
            ├── 001_<話ID>.html
            └── manifest.json               # 採点入力の唯一の正
```

同じ作品を取り直した場合は上書きせず、`captureId` の別サブディレクトリに新しい
スナップショットとして保存する（原本は不動）。ファイル名の連番は人間向けの飾りで、
意味のある取得順は manifest が正とする。

### manifest.json ＝ 採点入力の唯一の正

「どの話を・どの順で・どう採点したか」という採点入力の事実は、manifest.json
**一箇所だけ**に持たせる。順序をファイル名・別のメタファイル・dataset.jsonl の
三箇所に重複させると、いずれ食い違って壊れるためである。ファイル名の連番などは
人間が眺めるための飾りにとどめ、意味のある順序は manifest を正とする。

manifest が持つ情報（実装で確定したフィールド名）：

- `site` / `workId` / `siteWorkId`：取得したサイトと作品ID（接頭辞付きキー）
- `fetched`：取得した全話 `{ episodeId, url, order, file }` の配列（取得順）
- `decision`：採点入力 `{ sampledCount, targetEpisodeIndex, openingType, concatOrder }`
  （連結した話数・対象話・開幕形式・連結順）
- `pipelineVersion`：計算に使ったロジックのバージョン（現行 `line-meta-1`。後述）
- `captureId`：取得スナップショットの識別子（取得日時から生成）
- `capturedAt`：取得日時（ISO8601）
- `health`：健全性検証の結果 `{ healthy, reason? }`

数値（12指標・行メタ）は原本から `deno task separation` 等が再計算するキャッシュであり、 manifest
には持たせない。原本と manifest から `sampledCount` 等の採点入力を再現し、
再フェッチなしで数値を作り直せる。

### 再現と再実験を分ける（凍結 decision の扱い）

保存済み原本に対する再計算には、目的の異なる2つの操作があり、これらを混同しない。

- **再現（reproduce）**：保存時の数値をそのまま作り直す操作。採点対象は
  `manifest.decision`（`targetEpisodeIndex` と `concatOrder` を `fetched` の取得順に適用）
  **だけ**から組み立て、サンプリング判定（`selectSamplingTarget`）や開幕形式判定を
  呼び直さない。これにより、将来サンプリング/開幕判定のロジックを変えても、同じ原本からは
  常に収集時と同じ数値が再現される。manifest が「採点入力の唯一の正」であることの実体はこれである。
- **再実験（re-experiment）**：保存済み**全話**に現在のサンプリングロジックを再適用し、
  採点対象を選び直す操作。開幕形式の判定やサンプリング規則そのものをオフラインで検証するための
  もので、全話を保存している利点（採点対象でない話も残す）はここで活きる。再実験は再現とは
  別物であり、収集時の凍結 decision を上書きしない。

収集時は、サンプリングを一度だけ走らせて `decision` を確定し manifest に凍結する。保存する数値は
その凍結 decision を読む「再現」で算出する。したがって保存値と再現値は構造的に一致し、その一致は
後からロジックが変わっても保たれる。

### キー設計

作品の識別子には**サイト名を接頭辞として付ける**（例：`kakuyomu:822139843750356709`）。
これは、今後なろうに対応したときに作品IDが衝突しないようにするためである。
また取得日時（captureId）を持たせ、同じ作品を取り直した場合は上書きではなく
**別のキャプチャ（取得スナップショット）**として扱う。

### パイプラインのバージョン

「平均字/行」などの数値は、本文をどう行に区切り、どう文字を数えたかに依存する。
数え方のロジックを後で変えると、昔の数値と新しい数値が比較できなくなる。そのため
各レコードに「どのバージョンのロジックで算出したか」を記録する（manifest の
`pipelineVersion`）。原本のHTMLは再パースできるので、ロジックを変えても原本から 作り直せばよい。

### dataset.jsonl の新フィールドと後方互換

新形式の収集レコードには、原本への参照と行メタを持たせる：`captureId`（原本の
スナップショット）、`siteWorkId`（labels との join キー）、`bodyHash`（採点対象本文の
ハッシュ。転載重複検出用）、`lineMetadata`（行メタの分子・分母）、`eligibility`（収集
経路の由来マーカー。新形式は `"collected"`）。

旧クロールで貯めた既存レコード（行メタ・原本なし）は再フェッチせず、そのまま読める
（新フィールドは任意）。行メタ分析は `lineMetadata` を持つレコードだけを対象とし、 `lineMetadata`
を持たない旧レコードは分離度計算から外す。**外した件数は必ず出力し、 暗黙に間引かない。**

## ラベル運用

### 2つの軸を分ける

ユーザーの判定は、意味の異なる2つの軸に分けて記録する。

- **品質軸**：良 / ゴミ。文体そのものの良し悪し。
- **スコープ軸**：対象 / 対象外。そもそもこのフィルタの守備範囲かどうか。
  例：「文体は上手いが題材が好みでない」「AI補助だが破綻はしていない」作品は
  品質の良し悪しとは別に「対象外」となる。

対象外を品質判定に混ぜると、良/ゴミの分離度を測る計算が汚れる。よって両者を分けて
持ち、対象外の作品は分離度の計算から除外できるようにする。

（品質軸とスコープ軸を別フィールドで持つか、1フィールドの特別値で持つかは
実装の詳細であり、要件は「対象外を良/ゴミに混ぜないこと」である。）

### 収集コホートはタグで区別

「普通にランキングを巡回して集めた自然分布」「すり抜け駄文を狙い撃ちで集めた枠」
「ハードネガティブ」の区別は、別ファイルに分けず**同一ファイル内のタグ**で表現する。
個人利用の規模では、検索しやすければ1ファイルで十分である。

### 手作業でJSONを編集しない（操作性は必須要件）

ラベル付け・タグの付け外し・作品の除外は、すべて**コマンド（deno task）で実行できる**
ことを必須要件とする。JSONファイルを手で直接編集させない。イメージ：

```
deno task collect  <URL または作品ID>...            # 冒頭数話を取得し原本＋数値を収集する
deno task label    <URL または作品ID> <良|ゴミ|対象外> [note]  # 品質/スコープのラベルを付ける
deno task tag      <URL または作品ID> <+タグ|-タグ>   # タグを付ける／外す
deno task exclude  <URL または作品ID> [--undo]        # 分析対象から論理除外する／解除する
deno task separation                                 # 分離度と食い違いを出力する
```

`label` は品質軸（良／ゴミ）とスコープ軸（対象外）を1コマンドで受ける。良／ゴミは `scope=対象`
として品質軸に、対象外はスコープ軸に載せ、両者を混ぜない（対象外は分離度
計算から除外される）。既収集でない作品にはラベルを付けない（存在検証）。

作品の「除外」は**論理的な除外**（`excluded` フラグ）とし、保存済みHTMLの物理削除は
行わない。原本を消すと過去の実験を再現できなくなるためである。スコープ軸の「対象外」も
論理除外も、どちらも分離度計算から外れる（前者は守備範囲外、後者は分析からの一時除外）。

## 評価と成功条件

### スコアへの効かせ方は実験後に決める

3指標を最終的にスコアへどう反映させるか（機構）は、今は決めない。データを集めて
実験してから決める。候補は次の3つ。

- **新メトリクスとして加点式に混ぜる**：どの作品にも広く安定して効くなら妥当。
- **複合ペナルティ**：「平均字/行が低い かつ 地の文短行率が高い かつ メタ率が高い」を
  同時に満たしたときだけ減点する。特定の失敗パターンだけを狙い撃ちし、良作への
  副作用を抑えられる。単独指標での誤判定を避けたい場合に妥当。
- **足切りゲート**：複合条件を満たしたら閾値に関係なく除外する。

いま集めるべきは「この3択を見極められるデータ」であり、機構の決定はその後に回す。

### 成功条件

AUC などの統計指標だけで良否を判断しない。閾値40での実際の害と統計指標はずれるため、
主たる判定は次の2つで行う。

- **現行スコアで通過してしまう駄文を、新しい仕組みで何件止められたか。**
- **同じような見た目（短行・会話主体）の良作を、誤って何件巻き込んでしまったか。**

統計指標は補助にとどめる。

### 分析時の交絡・リークへの注意

- **交絡の回避**：3指標の効果を測るときは、本文の抽出ロジックを固定する。
  本文抽出を同時に変えると、スコアの改善が3指標のおかげなのか抽出変更のおかげなのか
  区別できなくなる。
- **リークの回避**：アンカーと広域サンプルで、同一作者・同一シリーズ・転載による
  重複本文が両側にまたがらないよう監視する。またがると、3指標が効いているように
  見えても、実は作者やシリーズの癖を拾っているだけ、という誤判定が起きる。
  作者情報と本文のハッシュ値で重複を検出できるようにする。

## スコープ外

- 作品の全話ダウンロード（採点対象の冒頭数話のみ保存する）。
- サンプリング規則・開幕形式フィルタそのもののチューニング（必要になった時点で別途）。
- 本格的なデータウェアハウス的な設計（イベント履歴、コホートの版管理、
  依存関係の完全記録など）。個人利用・数十〜200件規模には過剰なため採らない。
- なろう用の本文抽出の実装（本仕様は保存・ラベル・分析の枠組みを定めるもので、
  なろう対応は別スコープ）。
